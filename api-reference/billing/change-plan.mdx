## Overview

Changes the organization's billing plan. Handles upgrades and downgrades with automatic proration. Validates that current usage fits within new plan limits before changing.

## Authentication

Requires a valid Clerk session token. User must have `owner` role in the organization.

## Path Parameters

<ParamField path="org_id" type="string" required>
  The unique identifier of the organization
</ParamField>

## Request Body

<ParamField body="planId" type="string" required>
  The plan identifier to change to (e.g., "plan_pro", "plan_free")
</ParamField>

<ParamField body="interval" type="string" default="month">
  Billing interval: "month" or "year"
</ParamField>

      ISO 8601 timestamp
    </ResponseField>
  </Expandable>
</ResponseField>

```python Python
import requests

response = requests.post(
    f"https://api.photomem.io/api/organizations/{org_id}/billing/plan/change",
    headers={
        "Authorization": f"Bearer {clerk_token}",
        "Content-Type": "application/json"
```

## Proration

<AccordionGroup>
  <Accordion title="How Proration Works">
    When you change plans mid-billing cycle:
    
    - **Upgrades**: You're charged the prorated difference for the remaining time
    - **Downgrades**: You receive a prorated credit applied to next billing cycle
    - **Same-day changes**: No proration if changing on the same day
  </Accordion>

  <Accordion title="Calculation Example">
    Upgrading from Starter ($29) to Pro ($99) with 15 days left in cycle:
    
    ```
    Days remaining: 15
    Days in cycle: 30
    Proration factor: 15 / 30 = 0.5
    
    Price difference: $99 - $29 = $70
    Prorated charge: $70 * 0.5 = $35.00
    ```
  </Accordion>

  <Accordion title="Payment Timing">
    - **Upgrades**: Charged immediately via saved payment method
    - **Downgrades**: Credit applied to next billing cycle
    - **Failed payments**: Plan change is rolled back
  </Accordion>
</AccordionGroup>

## Downgrade Validations

Before downgrading, the system validates:

<Steps>
  <Step title="Project Count">
    Current projects must not exceed new plan's project limit
  </Step>
  
  <Step title="Team Members">
    Current team size must fit within new plan's member limit
  </Step>
  
  <Step title="Storage Usage">
    Current storage must be under new plan's storage limit
  </Step>
  
  <Step title="Active Webhooks">
    Active webhooks must not exceed new plan's webhook limit
  </Step>
</Steps>

If validation fails, you'll receive a 400 error with details about what needs to be reduced before downgrading.

## Best Practices

- **Monitor Usage**: Check current usage before downgrading
- **Delete Unused Resources**: Remove unused projects, webhooks, etc. before downgrading
- **Timing**: Change plans at the end of billing cycles to minimize proration
- **Test First**: Verify the new plan meets your needs before committing
